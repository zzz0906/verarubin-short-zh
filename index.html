Vera Rubin 能否准确运行 3-bit LLM 推理？

我们只研究一个问题：Rubin 的原生 LUT-B 指令能否运行 3-bit 模型权重和 3-bit KV cache，同时不破坏模型质量？

答案是可以——但必须使用正确的量化算法。 经过校准的非均匀码本与 scale 能把质量损失控制在合理范围； 朴素 3-bit 量化会使模型坍缩。决定 INT3 是否可用的是算法，而不只是位宽。

Rubin LUT-B 与我们的算法

Rubin 提供什么 一条原生 decompress::lut::b MMA。每个 3-bit index 从 Tensor Memory 中的 8 个 E4M3 值里选择一个，因此不需要独立反量化 kernel，也不会生成稠密 B 张量。
我们提供什么 离线量化器决定 8 个码本值、每个元素的 index 和 scale layout； runtime 则把模型权重或缓存 K/V 映射为压缩的 B 操作数。
1 · 调整分布按需旋转或缩放张量，削弱 outlier。
2 · 拟合码本为每个 tile 学习 8 个 E4M3 重建值。
3 · 保护误差按需用 RMS²、Fisher 或 GPTQ 保护重要误差。
4 · 打包保存 3-bit index、8 值 LUT 与 UE8M0 scale。
5 · 执行Rubin 在 MMA 内查表恢复 B；A 保持 E4M3。
一个 K64×N8 tile 包含 512 个 3-bit index（192 B）、一个 8 项 E4M3 LUT（8 B）和 scale metadata， 合计约 3.2 bits/weight。原生路径不会物化稠密 BF16 权重。

Kernel 如何计算矩阵乘

Kernel 仍然计算普通的 Y = A·B，但 B 只在每条 MMA 内部从 payload 重建。

B̂[k,n] = global × scaleB[t,n] × LUT[t][index[k,n]]
Y[m,n] = Σₜ Dₜ[m,n] × scaleA[m,t] × scaleB[t,n] × global
1 · 切分 GEMM。 一个 128-thread CTA 负责一个 M128×N8 输出 tile，并以 64 元素为一段遍历 K。 激活按 row/K block 量化为 E4M3 与一个 UE8M0 scale。
2 · 搬运 payload。 3-bit index 被重排为指令要求的 256-byte shared-memory image； 对应的 8 值 LUT 与 A fragment 被放入 Tensor Memory。
3 · 发射原生 LUT-B。 Kernel 执行 tcgen05.mma…decompress::lut::b。 硬件查表恢复 B 并累加 FP32 partial D；mbarrier 保证 MMA 完成后才读取 D。
4 · 应用 scale。 Epilogue 把每个 partial 乘以 activation scale、weight scale 和 folded global scale。 two-K32 配方使用两遍 masked K64，因为这条指令不能直接执行 K32 LUT-B。

集成方式很直接：Qwen/Gemma 替换文本 nn.Linear；MiniMax 替换 routed-expert W13/W2 GEMM；KV attention 在 QK 与 PV 收缩中把压缩 Kᵀ 和 V 映射到 B。

这个 kernel 的主要挑战

只能解压 B。 压缩矩阵必须是操作数 B。这会约束 attention schedule： Q×Kᵀ 与 P×V 可以直接使用 LUT-B，把长 K/V 放在 A 的 schedule 则不行。
Scale 的位置。 Activation 与 weight scale 会随 tile 变化。当前正确性 kernel 需要读回每个 FP32 partial 后再乘 scale， 因而不能让 partial 在整个 K loop 中一直留在 Tensor Memory。
Small-M 利用率。 原生 M tile 有 128 行；batch-1 decode 或稀疏 routed expert 往往只有几个有效行。 生产性能需要 batching、expert gathering 或 persistent schedule。
two-K32 与同步。 细粒度 K32 scale 需要两遍 masked K64。TMEM store、MMA、mbarrier 完成与 FP32 读取也必须正确排序； 当前 MiniMax 精度路径使用 launch blocking 保证确定性。

实验一：3-bit 权重

我们比较了 18 种量化配置，另加 BF16 与 A8 baseline， 覆盖 Qwen3-4B、Gemma4-12B、MiniMax-M3 和 8K/64K/128K 三种上下文。 核心问题是：算法选择能否让原生 W3A8 真正可用？

对比算法分别做什么

Lloyd–Max / uniform / NF3。 Uniform 把 8 个值均匀排开；NF3 使用固定的正态分布码本； Lloyd–Max 针对每个 tile 学习 8 个质心，用来判断“拟合码本”本身是否重要。
RMS² / SqueezeLLM。 RMS² 按 activation second moment 加权重建误差； SqueezeLLM 使用 diagonal Fisher。两者都改变码本拟合，但都不是 GPTQ 误差补偿。
GPTQ / inter-GPTQ。 GPTQ 使用 block Hessian，把舍入误差推给尚未量化的列； inter-GPTQ 则让补偿 sweep 与 8 值码本重拟合交替进行。
H64 / AWQ / scale 变体。 H64 用带符号 Hadamard 变换打散 outlier，并对 A 应用匹配变换； AWQ 重缩放 activation channel 并把逆 scale fold 进权重；K64/two-K32/global 改变 scale 粒度。

上图报告的量化 GEMM 全部通过 Rubin 原生 LUT-B MMA 执行。

结论：3-bit 权重可行，但朴素码本可能差几个数量级。

实验二：3-bit KV cache

Figure 2 比较 5 种 Qwen KV 配置（BF16 加 4 种压缩方案）和 3 种 Kimi latent-cache 配置。 它检验经过拟合的码本与受控 scale 能否在减少 cache traffic 的同时保持原生 K3V3 精度。

KV 算法分别做什么

Window 与 sealing。 Sink 和 recent tokens 保持 BF16。更旧的 K/V 只封装一次，按 64-token chunk 存为 3-bit index、layer-specific LUT 和 scale；decode 不再改写它们。
Lloyd–Max 码本。 每层从校准数据学习 8 个非均匀值，把分辨率放在 K/V 真正出现的位置； uniform 会把码字浪费在稀疏尾部并导致 PPL 坍缩。
OSCAR。 校准得到的 rotation 与 clipping 在拟合码本前打散 outlier。 它在部分模型上有益，但如果不能吸收到相邻 projection，就会引入 runtime transform。
原生 attention 路径。 E4M3 Q 乘压缩 Kᵀ；max、exp、sum 与 normalization 保持 FP32； E4M3 P 再乘压缩 V。两次 cache 读取都使用 B-side LUT 解压。

结论：从 PPL 看，只要控制好码本与 scale，3-bit KV 就是可行的； uniform INT3 不是可用 baseline。

结论一：W3A8 大多数复杂精度算法都在离线完成，并保留单遍 K64 kernel。 H64 需要 A transform；two-K32 需要第二遍 MMA。
结论二：K3V3 拟合码本并控制 scale，可把 1M KV cache 从 154.6 GB 降到 30.2 GB。 实际速度随后取决于 LUT-B rate 与 small-M schedule，而不需要额外反量化 pass。

为什么这些是真实 Rubin 结果

物理 payload 权重与缓存 K/V 以 3-bit index、8 值 E4M3 LUT 和 scale 存储，而不是稠密 BF16 张量。
原生指令 Kernel 发射 tcgen05.mma…decompress::lut::b；解压发生在 MMA 内部。
没有模拟 fallback 已发布 MiniMax 实测均为 sim_fallback_gemms = 0。模拟与硬件对排序和坍缩结论一致。

研究边界

这是一个精度研究，不是经过优化的吞吐声明。 当前 kernel 有意以正确性优先；更快的调度、batching 与 pipelining 属于后续工程， 不影响上面的质量结论。
